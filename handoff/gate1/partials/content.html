  • Reference page at /components/<id>/reference: the whole file rendered, with a "try it" action on every live block that opens it in the editor.

## Platforms Code reference (evidence and open items)
  • GitHub highlights each block by its first word and ignores the rest of the line, so the file reads as ordinary Markdown there. This could not be confirmed against GitHub's renderer from this environment.
  • The build groups blocks by example name. It fails if a framework is missing from a group, if a block does not compile, or if the four variants do not render the same result.
  • Markdown is rendered through package components (tables, links, alerts, code blocks), not through injected HTML, so the reference page is an honest render too.

Two languages without duplicated facts

  • English file plus Arabic sibling. Prose is translated; code blocks and API tables are identical and are checked to be identical.
  • A structure check requires the same headings and the same example names in both files, and flags an Arabic section whose English source changed after it.

What this replaces

  • The guide's 83 generated component pages, where about 31% of each page is text repeated word for word on every page.
  • API tables kept separately in guide source and in package READMEs, which disagree with the code and with each other (component counts of 77, 81, 82 and 83 appear in different documents).
  • Twelve guide articles stored once in English and once in Arabic in TypeScript, with drift between them.

What the content audit measured

  • 26 clusters of duplicated facts. The identity sentence exists in more than 15 copies, the disclaimer in about 60 files, the package map in 8, and the calendar range in 16.
  • Whole paragraphs are repeated across three to five package READMEs and PORTAL files.
  • Arabic terminology competes for the same concepts (adapter, accessibility, tokens, variant, styles); the rebuild needs one glossary.
  • The audit produced a disposition (keep, merge, supersede) for each of the 69 files in docs/; it is in the findings under Content and tone.
