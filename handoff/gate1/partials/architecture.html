Proposed structure

  • Location. guide/ at the repository root, outside the workspace globs, with its own lockfile. It depends on exact versions of the seven packages and nothing else from this repository except the Markdown content.
  • Rendering. Angular CLI 22 with static output, client hydration, base href from HAWIYAH_BASE_PATH, a generated 404.html. Routes carry the locale (/ar/…, /en/…). Direction and colour mode are reader choices applied by a small inline script before first paint. Old hash links are redirected.
  • Honest render, made enforceable. Guide CSS may place and space things with tokens. A lint step fails on any selector that targets .hw-*, on raw colours and on physical properties. No server DOM shim and no skipped hydration, because both would hide package defects. Third-party engines stay behind the documented integration boundary (the code editor surface is one).
  • Registry check in CI. Fails if any @hawiyah/* package comes from a link, a tarball, an override, an alias, a path import, or a version other than the pin, and compares installed integrity with the registry. It runs before the build and again before deploy. The prerender log is also scanned, because the build can exit 0 with server errors.
  • Editor. Published files served unmodified through an import map in a sandboxed frame, the Angular linker applied at build time, examples precompiled, compilers loaded on first edit (Sucrase for JavaScript and JSX, the Vue compiler, TypeScript with the Angular transform). The status bar shows package, version and registry integrity.
  • Tests. The guide gets its own unit suite (Vitest ran out of the box) and a Playwright suite against the static output under /hawiyah/, with axe, direction and reduced-motion checks. A new workflow runs package and guide checks on every push and pull request.

Package gaps the guide depends on

  • Server rendering and hydration: the eight components above, plus deterministic ids. Each fix needs a render and hydration test in the Angular package so it cannot regress.
  • Stylesheet entry: the published styles.css imports the tokens package by bare name and cannot be loaded by a browser without a bundler. A flat published file fixes that and the 48-file import chain.
  • Documentation shell: the layout primitives cannot yet lay out a documentation site without extra CSS (nothing is sticky, navigation does not collapse below 64rem), and neither ContentNavigation nor TreeView can serve as a cross-page sidebar because they have no link items. Link components also need Angular Router integration.
  • Fragment links under a base path: the packaged skip link and ContentNavigation links resolve to the site root under <base href="/hawiyah/">, which breaks skip-to-content on GitHub Pages (WCAG 2.4.1).
  • Missing components: a code block with copy and syntax colour tokens, prose typography for long text, and a grouped search dialog.
  • Fonts and motion: the allowed packages give no way to load IBM Plex Sans Arabic, and the generic motion tokens have no recorded Platforms Code source. Reduced motion is honoured: all 39 motion declarations in the published styles reset under it.
  • Icons: 22 of the 38 icons the current guide uses are not shipped in the styles package, though all 38 match the pinned Hugeicons commit. They need adding to the package from that commit.
  • Scale of guide-only CSS today: of 1,527 rules, 549 are page composition, 87 restyle package components, 252 imitate components the packages already ship, 384 cover needs no package meets, and 255 are dead.
  • Templates: across the 17 templates, roughly a third of the visual blocks are guide-only. Most can use a component that already exists; the true gaps include a hero, a prose style for long text, a link list, a chat log, and a reasons step for Feedback.

Previewing unreleased package work

A separate workflow builds the guide against tarballs produced by check:packages, shows a persistent notice naming the commit, sets noindex, and uploads the result as a workflow artifact. It has no Pages permission, so it cannot reach the deployed site. The same build runs locally with one command. Release candidates can instead be published under the next tag, each with your approval, and the guide pinned to them on the branch.

Trusted publishing

  • One-time setup on npm, with your account: npm trust github @hawiyah/<name> --file publish.yml --repo MohamedEmbarak/hawiyah --env npm --allow-publish --yes for each of the seven packages. The first call asks for 2FA and offers to skip it for five minutes, which covers the rest. It needs npm 11.15 or later.
  • A new configuration expires unless a publish succeeds within two days, so set it up immediately before the next release.
  • Per release: pushing the tag starts publish.yml; the job waits in a GitHub environment named npm that lists you as required reviewer; one approval publishes all seven with provenance. No token and no 2FA prompts.
  • Afterwards: set each package to require 2FA and disallow tokens, delete the NPM_TOKEN secret, and remove the token line from the workflow.
  • Build hygiene in the same change: clean dist before building and compare the packed file list with a clean build. That closes the stale-asset problem found in 0.2.1.
